### 必须保留的架构与权限规则

- 私人笔记和图片都检查所有者；管理员身份不提供读取其他用户私人内容的通行证。跨用户拒绝行为包含返回 `404` 的现有约定。
- 图片使用“私有 OSS + 后端图片代理”：浏览器访问同源接口，经身份、所有者与短期凭证检查后读取图片。当前不依赖浏览器直连 OSS 或 OSS 自定义域名。
- 数据流：浏览器 → 同源 `/api/v1` → FastAPI → PostgreSQL / 存储适配器；Worker 独立领取任务并生成图片变体。
- 笔记更新依赖 revision 避免覆盖；不要为简化保存而移除冲突检查。
- Worker 业务写入需要遵守租约与幂等边界；旧租约执行者不能覆盖新执行结果。
- Outbox 与业务变更在同一事务保存；通知投递保持现有幂等性。
- 目前不需要为新任务预先引入 Redis、微服务或 Kubernetes，优先沿用项目已有模块和工具链。

## 6. 伙伴首次本地启动

前端使用 Node.js 22、npm；后端优先 Python 3.12，与 CI/容器一致，使用 `uv` 和项目虚拟环境。不要使用维护者机器路径、账户、数据库或凭据。后端依赖见 `backend/pyproject.toml`、`uv.lock`、`requirements-dev.lock`，前端依赖见 `frontend/package.json`、`package-lock.json`，版本以锁文件为准。

最容易的功能体验方式是项目根目录的 Docker Compose，默认本地存储，不需要真实 OSS 或模型 Key。以下为 Windows PowerShell，新克隆目录中执行；每条命令成功后再继续：

```powershell
py scripts/init_env.py
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose exec api python -m app.cli create-admin --username admin
```

访问 `http://localhost:8080`；健康接口为 `/api/v1/health/ready`。管理员密码由伙伴自行交互输入，没有默认管理员密码。`scripts/init_env.py` 只用标准库生成随机本地配置，已存在时拒绝覆盖；不要把 `.env` 输出或提交。

需要频繁改代码时，按本地开发文档设置独立的 `compose.dev.yaml` 数据库、`backend/.env`，用项目 venv 启动 API/Worker，再运行 Vite；不要假定 `.local/postgres.env` 已随 Fork 提供。API 与 Worker 使用同一配置和本地存储目录。开发数据库常用端口为 `55433`，临时测试库为 `55432`。

若本机已有其他克隆或同名 Compose 项目，先确认端口、项目名与数据卷归属再启动，避免复用他人的数据库。`stop` 保留数据；不要对有重要数据的环境执行 `down -v`。

### API 变更时同步生成

在已配置隔离环境的 `backend` 目录执行，再进入 `frontend`：

```powershell
uv run python -m scripts.export_openapi
Set-Location ../frontend

```

同步提交 `backend/openapi.json` 与 `frontend/src/api.generated.ts`。不要手工修改生成类型或放宽检查来掩盖差异。此前已修复 Python 3.12/3.13 的 HTTP 422 描述差异和 JSON 属性顺序漂移；契约检查包含 UTF-8/LF 与完整序列化文本一致性。

每个 PR 跑相关测试；涉及权限、队列、数据库迁移、公共契约或模块联动时补足对应回归。用新结果记录命令和通过/失败/未运行项；历史 CI 成功不替代新 PR 的 CI。纯文档变更一般无需启动业务服务或重跑全量测试。

## 8. Fork 与 PR 协作流程

建议约定：原仓库 `main` 是集成基线，伙伴在自己的 Fork 中为每个任务创建分支，向原仓库 `main` 发 PR。一个 PR 聚焦一个任务或一组必须一起交付的改动。

在 GitHub 点击原仓库的 Fork。以下为伙伴本机 PowerShell 示例，先替换自己的 GitHub 用户名：

```powershell
$forkOwner='你的GitHub用户名'
git clone "https://github.com/$forkOwner/ai-notes.git"
Set-Location ai-notes
git remote add upstream https://github.com/lixiaobai405-spec/ai-notes.git
git remote -v
git fetch upstream
git switch main
git merge --ff-only upstream/main
git switch -c codex/task-short-name
```

其中 `origin` 指向伙伴 Fork，`upstream` 指向原仓库；`codex/task-short-name` 替换为任务分支名。已有克隆先检查远程地址和未提交改动，不重复添加远程。若不能快进合并，先分析分叉，不强制覆盖本地工作。

任务流程：

1. 双方先确定目标、改动范围、验收标准和容易重叠的文件；没有分配的待办不自行扩展。
2. AI 先读项目说明和相关代码，再完成该任务；不做无关重构，不擅自增加依赖或改变部署方式。
3. 完成必要验证后，检查 `git status`、`git diff` 和暂存区；明确选择任务文件，不使用广泛暂存把私密文件或临时输出混进去。
4. 获得伙伴本人的提交/推送授权后提交英文 commit message，只推送自己的任务分支：`git push -u origin codex/task-short-name`。
5. 在原仓库创建 PR：base repository 为 `lixiaobai405-spec/ai-notes`，base branch 为 `main`；head repository 为伙伴 Fork，compare branch 为任务分支。
6. 等待 CI、维护者 review（审查）与反馈，修改继续推送同一分支；合并由维护者确认。不要自动合并或直接推送原仓库 `main`。

任务期间上游有更新，可在干净的任务分支执行 `git fetch upstream`，再 `git merge upstream/main`，解决冲突并重跑受影响检查。共享分支优先采用不改写历史的方式，避免强制推送。

### PR 描述至少包含

- 解决什么问题、修改后的实际行为、任务范围。
- 关键文件或架构取舍；API 是否改变，两个生成契约是否同步。
- 数据库 migration（迁移）是否新增，既有数据兼容性、升级与回退限制。
- 实际运行的验证命令、结果、跳过项及原因；UI 修改附适当截图或操作证据。
- 新增配置变量只说明名称和示例值，不包含真实凭据。
- 剩余风险、已知限制、需要维护者决定的事项。

较大任务可在 `docs/task-evidence/` 增加对应证据文档；历史失败、当前通过和人工验收分别陈述，不补造没有保留的测试过程。

## 9. CI、发布与部署权限
