## 更新前检查

先核对实际运行版本、数据库revision、镜像摘要、Compose项目与完整文件集合、数据库/文件/证书原卷、对象存储前缀及备份恢复点。公网已有IP HTTPS和卷保护覆盖，必须沿用本地私密运维记录的完整集合；不能单独套用旧HTTP命令或创建同名新空卷。登录服务器前读取项目AGENTS指定的连接、当前运行及监测记录。本说明不替代那些实际环境记录，生产变更按当次任务授权执行。

以下命令在目标运维主机的项目目录执行。先把占位符替换为该环境已核验的完整参数，不读取或打印私密环境文件内容：

```powershell
$M4ComposeArgs = @('--env-file','<PRIVATE_COMPOSE_ENV_FILE>','-p','<EXISTING_PROJECT>',
  '-f','<COMPOSE_FILE_1>','-f','<COMPOSE_FILE_2>','-f','<HTTPS_AND_VOLUME_GUARD_FILE>')
docker compose @M4ComposeArgs config --quiet
docker compose @M4ComposeArgs ps
docker compose @M4ComposeArgs images
```

`config --quiet` 应成功且不打印展开的凭据；其余输出用于核对实际容器与镜像。数组只展示参数结构，文件数量必须以实际记录为准。Ubuntu维护命令使用目标shell对应写法，不能直接粘贴PowerShell数组语法。

先用即将发布的源码、锁文件和精确profile，在空隔离环境演练旧备份恢复、向前迁移和全部对象核验。API、Worker、Web、数据库扩展镜像与工具快照分别核验；不能把更新Git或应用镜像当成更新独立监测/备份快照。

本期仍使用PostgreSQL16及pgvector0.8.7。旧profile和迁移摘要不能重写。不要从现有生产库生成“预期schema”来绕过严格检查；匹配当前revision的完整profile/guards与vector库存随备份工具一起交付。

## 停写、备份与更新

1. 安排维护窗口，阻止新编辑、上传、聊天、发布与AI提交；等待可完成任务，停止API和所有实际运行的Worker进程。新版默认Worker在单个进程内启动五条线程通道，共享该进程连接池；不能仅停某条通道就视为全部停写。
2. 记录当前revision及原镜像，使用匹配该revision的整站工具备份数据库和全部必需对象，校验包并保存主机外副本。账号ZIP不能代替整站备份。
3. 在独立空库、空对象目录执行实际恢复，核验原数据/对象摘要及恢复后的运行状态。备份文件存在、校验器成功或健康检查均不能单独证明恢复成功。
4. 按既有完整Compose集合切换核验过的镜像；在API/Worker仍停止时运行迁移，确认实际head及 `alembic check` 无漂移，再启API、Worker和Web。保留旧卷和原镜像回退点。
5. 恢复写入前逐项验收下文功能、权限、备份与监测身份；确认旧账号、原件和历史可读后再开放。

备份工具的命令结构如下；使用目标环境已确认的隔离Python环境，数据库URL通过私密文件传入，不写进命令行。`--maintenance-confirmed` 表示已经完成真实停写，并非工具会自动停服务。

```powershell
<PYTHON> scripts/site_backup.py backup --database-url-file <PRIVATE_DATABASE_URL_FILE> --postgres-container <EXISTING_DB_CONTAINER> --output <NEW_BACKUP_DIRECTORY> --storage-backend local --storage-root <EXISTING_PRIVATE_OBJECT_ROOT> --maintenance-confirmed --schema-revision <ACTUAL_SOURCE_REVISION>
<PYTHON> scripts/site_backup.py verify <NEW_BACKUP_DIRECTORY>
<PYTHON> scripts/site_backup.py restore <NEW_BACKUP_DIRECTORY> --database-url-file <PRIVATE_EMPTY_TARGET_URL_FILE> --postgres-container <ISOLATED_TARGET_CONTAINER> --storage-root <EMPTY_TARGET_OBJECT_DIRECTORY> --isolated-confirmed
```

OSS模式改为 `--storage-backend oss --env-file <PRIVATE_OSS_CONFIG>`，不再传 `--storage-root`。以上均为结构模板，占位符不能原样执行；真实OSS读取及公网维护须按当前任务授权执行。详细限制沿用 [整站备份与隔离恢复](整站备份与隔离恢复.md)。

## 发布后验证

- API就绪、旧账号、私人笔记/原图/PDF/回收站/历史、原有AI/卡片/测验/复习与社区功能正常；管理员无私人所有者旁路。
- 应用壳可安装与提示更新，私人API不进入共享缓存；用户主动推送授权/拒绝回退/退出撤销、通用锁屏提示分别实测。真机与真实推送不能用模拟视口替代。
- 同账号缓存全文/组织/原件后断网重开，编辑落盘并能人工同步；同字段冲突保留两侧，账号切换锁定旧资料，退出清理失败会提示。
- 共享模型按服务商+原模型ID选择；工具范围需预览确认，失败未知调用不自动重发；学习分析只发送已批准的冻结数字汇总，刷新仍保留原编号。真实外部模型会产生费用，须另有授权。
- 两API进程间聊天、通知多页补拉、另一设备已读、listener重连、Worker不同通道和租约恢复正常；反向代理必须支持 `/api/v1/realtime/ws` Upgrade。实时失效信号不能替代HTTP持久数据。
- 使用当前74表profile实际备份/恢复；核对监测专用角色仍可访问所需对象、连接网络与状态身份。数据库容器/网络更换前先处理原监测连接，后再恢复采集。

每API进程使用一个共享LISTEN连接，按进程批量重验当前会话。通知以owner内递增seq和read_revision补拉；断线、事件合并或丢失时仍依靠HTTP恢复。默认Worker在单进程内以jobs/ai/outbox/push/maintenance五条线程通道执行，共享该进程的SessionLocal和连接池，原 `--once` 保留单轮语义。发布前按实际API及Worker进程数、每进程连接池、独立认证/listener连接和维护/监测预留连接与内存；另启多个Worker时再按实际进程倍增，不能把五线程直接乘成五个连接池，也不能把本地100连接空闲样本当生产容量保证。

认证批次使用独立的惰性连接池，避免共享HTTP池耗尽时等待原30秒checkout。默认共享池5+5、listener1、auth1，每API配置预算12连接；两个API与一个默认Worker合计34，再另加监测/备份等连接。该值随实际环境池配置改变。认证池checkout100ms、建链2秒、SQL/锁800ms，关闭宽限4秒并真正排空后释放；每秒指调度周期，不是故障状态下严格撤销时延保证。raw auth查询不经过共享SQLAlchemy Engine，查询测量必须另外统计 `IdentityValidator.calls` 或PG应用名 `notes-realtime-auth`，不能把共享池计数为零称作总SQL为零。
