本文件是 M3 发布准备方案，不表示公网已更新，也不提供新的部署授权。

新表通过冻结 DDL 创建，M2 原表数据不重写；社区快照的来源 UUID 只用于历史身份判断，不授予私人内容权限。PostgreSQL16.8 + pgvector0.8.7 与 M2 保持一致。

## 更新前检查

1. 先阅读本地 `.local/ops/服务器连接与M1执行记录.md`、`公网当前运行与更新命令.md`、`监测运行与更新命令.md`，核对实际连接、完整 HTTPS Compose 集合、镜像 digest、当前生产卷/集群和备份调度。旧卷不等于当前库。
2. 获得发布授权后，按明确 M3 文件范围检查 Git diff 和同提交 CI；保留已有无关运维修改，不提交 AGENTS.md、.local 或真实环境文件。
3. 应用、Worker、API契约、迁移、账号验证恢复工具、整站备份 profile 必须属于同一发布。独立监测/备份运行快照需单独核验更新，更新 Git 或应用镜像不会自动更新它们。
4. 先在空的隔离库演练49→66迁移、原数据投影、账号 v4 与整站真实恢复，再安排生产维护窗口。健康响应或 Alembic check 不能代替数据恢复证据。

## 维护与验证

先阻止新写入，停止新上传/发送/发布，等待已有任务退出，停止 Worker 和 API。用当前真实 revision 的严格备份工具保存数据库、全部对象和主机外副本，并实际隔离恢复。

保持当前完整 HTTPS guard、固定生产卷、对象前缀与证书卷。切换核验过的应用/Worker/Web 镜像并迁移，不用旧 HTTP 配置替换当前 Compose 集合。反向代理需保留 `/api/v1/realtime/ws` 的 WebSocket 升级，开发 Vite 代理也已启用 `ws: true`。

开放写入前检查：旧账号/私人笔记/AI/学习功能、两成员好友与分享撤销、私聊与离线补拉、附件参与者权限、社区副本复制/撤回/下架、管理员边界、工作台与账号导出；核对新表备份、监测身份和实际工具快照。真实资料外发或付费模型不属于这些本地验证授权。

## 回退

开放新写入前按已演练恢复点回退，保留迁移后的卷用于排查。开放新写入后不能直接覆盖旧库或执行 downgrade：这会丢失新消息、附件、分享、社区内容与互动。先停写、保存新数据，再制定对账或向前修复方案。

迁移升降级循环只可用于可丢弃隔离库。生产故障不能以“测试曾降级成功”为理由执行破坏性降级。

## 账号 ZIP v4

共34类集合，保留 v1 的14类、v2的15类、v3的32类兼容。新增两个集合保存本人社交与社区历史及合法附件。外部成员使用按本账号隔离的假名标识；收到的只读分享只有记录，不携带对方笔记原文。

恢复仍只允许显式命名的本地空库和空文件目录，设置新密码并恢复为普通账号。社交数据成为只读历史，不重建外部账号/好友/授权/聊天线程/公开帖子，也不触发新消息或发布。私人恢复历史 API 每次检查 owner，管理员无旁路。完整创作、消息和资产仍可再次导出。

## 整站与文件保留

使用匹配当前 revision 的 `scripts/site_backup.py` 和精确 profile。新 profile 来自两份新建迁移库的真实 pg_dump/pg_restore，不从生产数据生成预期 schema。

备份覆盖聊天附件、已撤回/下架的社区副本、未完成复制的可选目标与所有非空冻结来源、恢复历史附件；必需对象缺失或同长度哈希损坏均拒绝。恢复先比对原指纹/对象，再撤销会话、删除实时票据并把未完成发布/其他任务置于中断终态，不自动重放。

文件保留审计将这些对象作为根，权限撤销不会让历史文件成为垃圾；未知任务类型或损坏引用仍拒绝整次清理。具体维护方式继续沿用[整站备份](整站备份与隔离恢复.md)和[文件引用保留](文件引用保留与安全清理.md)，不得直接清空对象目录。
